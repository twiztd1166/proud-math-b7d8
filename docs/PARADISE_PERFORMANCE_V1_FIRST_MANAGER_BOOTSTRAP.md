# Paradise Performance v1 — First Manager Trusted-Device Bootstrap

Status: WORKING CONTROL / CONTROLLED TESTING ONLY / NOT EMPLOYEE-ROLLOUT AUTHORIZATION

## Purpose

Normal Paradise Performance enrollment is manager/admin-issued. A signed-in, currently enrolled manager/admin uses `performance-enrollment-mint` to create a short-lived one-time enrollment secret for an active employee. A fresh environment has no such trusted privileged device, so one bounded initialization path is required.

The controlled first-admin sequence uses two server-side functions:

- `performance-first-manager-bootstrap-provision` — consumes a one-time out-of-band proof and creates only the temporary Auth user required to start the bootstrap.
- `performance-first-manager-bootstrap-mint` — verifies that temporary Auth user, mints the ordinary 10-minute enrollment secret, then disables the temporary Auth identity before handing the secret off.

Neither function replaces ordinary trusted-device enrollment after initialization.

## Preconditions

1. The target is an explicitly approved real active Paradise manager/admin row.
2. The target is not either synthetic marketplace-review identity.
3. No historical real manager/admin Performance actor identity may ever have existed. Revocation does not reopen bootstrap.
4. A high-entropy out-of-band proof is generated by an authorized operator and delivered only to the intended admin through a separate controlled channel.
5. `performance_bootstrap_challenges` stores only SHA-256 hashes of the proof and authorized email plus target employee UUID, expiry and consumed timestamp. The table is RLS-enabled and inaccessible to public/anon/authenticated clients.
6. No plaintext proof, temporary password, session token, service-role/secret key or resulting enrollment token may be stored in GitHub, Drive, chat, screenshots or logs.

## Controlled sequence

1. Authorized operator inserts one challenge row containing only `proof_hash`, `email_hash`, approved target `employee_id`, and short expiry.
2. Plaintext proof is sent only to the authorized admin's separate email inbox.
3. The admin opens the controlled `first-admin-bootstrap.html` page on the intended private browser and enters the authorized email + proof.
4. The browser generates a high-entropy temporary password in memory. It is never displayed or persisted.
5. The browser calls `performance-first-manager-bootstrap-provision`. This endpoint has `verify_jwt=false` only because no Auth user exists yet; its credential is the high-entropy out-of-band proof.
6. The provisioning function hashes email/proof, resolves the matching unconsumed/unexpired challenge, verifies the target is a real active manager/admin, rejects synthetic identities and refuses to proceed if any real privileged Performance lineage exists.
7. The provisioning function consumes the challenge before Auth creation. If Auth creation fails, that proof is burned and a new operator-issued proof is required.
8. The function creates the temporary user only through supported server-side `auth.admin.createUser`, confirms the email because the separate proof has already established possession of the authorized channel, and sets only the exact bootstrap `app_metadata` expected by the JWT-gated mint.
9. The browser signs into that temporary user with the in-memory password using a non-persistent Supabase Auth client and invokes `performance-first-manager-bootstrap-mint`.
10. The mint independently revalidates global one-time/privileged-lineage controls, creates the ordinary 10-minute trusted-device token, and disables/bans the temporary Auth identity before returning the token. If disabling fails, it revokes the enrollment token and returns no usable bootstrap result.
11. The browser signs out the temporary Auth session and immediately redeems the one-time enrollment token through the ordinary `performance-enrollment-redeem` path using platform `web-test`.
12. Ordinary redemption creates the hidden device Auth user, actor identity, trusted-device row and persistent revocable web session. The bootstrap page then redirects to Paradise Performance.
13. The first trusted admin must enroll the second test admin through the normal `performance-enrollment-mint` flow. The exceptional first-admin path is not reused.

## Hard prohibitions

- Never insert, update or delete managed `auth.*` records directly with SQL for bootstrap.
- Never use a `SECURITY DEFINER` database Auth-provisioning shortcut.
- Never ship a service-role/secret key to browser/app code.
- Never store plaintext out-of-band proof or temporary password in the challenge table or source.
- Never allow request-body employee UUID selection for proof provisioning or bootstrap mint.
- Never reuse either synthetic marketplace-review identity for real testing/rollout.
- Never use the exceptional path after any real privileged Performance actor lineage exists.
- Never treat bootstrap as Privacy/HR approval, employee-rollout authorization, or native background-GPS validation.

## Completion evidence

Bootstrap is complete only when all are true:

- approved real first-admin row is active;
- hashed challenge is short-lived, one-time and consumed;
- temporary Auth user is created through supported server-side Auth Admin API;
- bootstrap mint succeeds;
- temporary bootstrap Auth identity is disabled before token handoff;
- ordinary trusted-device redemption succeeds;
- first real admin actor identity/device readback is correct;
- first admin can mint a fresh ordinary token for the second test admin;
- no synthetic review identity is used;
- no plaintext credentials or privileged secrets are stored in controlled documents/source;
- broader employee rollout remains separately authorized.
