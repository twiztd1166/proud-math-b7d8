# Paradise Performance v1 — Deep Design Audit

Status: **PRE-IMPLEMENTATION DEEP AUDIT — SPECIFICATION ONLY — NOT PRODUCTION AUTHORIZED**  
Date: 2026-08-18  
Controlling design: `docs/PARADISE_PERFORMANCE_V1_SPEC.md`

## Executive disposition

The proposed Performance architecture is viable and materially simpler for the canvasser than a conventional CRM/timekeeping/KPI application. The central design survives the first adversarial pass provided implementation preserves the controls below.

**Recommended disposition: PROCEED TO ISOLATED IMPLEMENTATION FOUNDATION.**

This is not a production-release determination.

## 1. Highest-risk design failures and dispositions

### A. Local-only Performance storage

**Risk:** using the existing Training/localStorage pattern would create multiple inconsistent employee/device records, make team maps/leaderboards impossible to trust, and weaken customer/pay auditability.

**Disposition:** CLOSED BY DESIGN. Performance uses a central authoritative Postgres source with local state only as offline queue/cache.

### B. Traditional employee account friction

**Risk:** email/password/login/reset flows would make field adoption unnecessarily difficult.

**Disposition:** CLOSED BY DESIGN. One-time trusted-device enrollment plus revocable session; shared-device name + PIN fallback.

### C. “No accounts” becoming “no authentication”

**Risk:** a shared unauthenticated application would allow one employee to submit/edit another employee's records.

**Disposition:** CLOSED BY DESIGN. No traditional account UX, but every write is authenticated to an employee/device session. Visibility parity does not imply mutation parity.

### D. Shared visibility accidentally granting shared edits

**Risk:** user requirement that canvassers see everything managers see could be implemented as broad database access allowing record mutation.

**Disposition:** MUST BE MACHINE-TESTED. Shared SELECT visibility is separate from row/endpoint mutation policy. Employees may not alter other employees' source records.

### E. Demos/Sales divided by the wrong hours

**Risk:** a sale occurring Friday could be incorrectly treated as generated by Friday's newly worked hours even though it originated from a Monday Set.

**Disposition:** CLOSED BY DATA MODEL. Store event date and origin cohort. Official KPI configuration must explicitly select attribution semantics. UI explains the model.

### F. Pending appointments treated as failed outcomes

**Risk:** current-day/week Demo/Sale rates and rankings become artificially bad merely because appointments have not occurred yet.

**Disposition:** CLOSED BY DESIGN. Pending outcomes remain PENDING; maturity is displayed and denominator eligibility is explicit.

### G. Tiny-sample leaderboard gaming

**Risk:** one Set in 30 minutes can produce an artificially dominant Sets/Hr ranking.

**Disposition:** CLOSED ARCHITECTURALLY / THRESHOLD OPEN. Ratios can be PROVISIONAL until controlled minimum hours/opportunities are met. Exact thresholds still require Paradise input.

### H. Working fewer hours to protect efficiency rank

**Risk:** pure per-hour leaderboards create incentives to suppress hours/volume.

**Disposition:** CLOSED BY DISPLAY/RANKING DESIGN. Raw production and efficiency are shown together; Overall score, if added, requires approved weights/guardrails.

### I. Employee-entered Sets total mismatching customer records

**Risk:** employee says five Sets but enters four customers.

**Disposition:** CLOSED BY MODEL. Sets are derived from persistent Set records; there is no independent typed Set total.

### J. Duplicate Sets from offline retry

**Risk:** poor service causes a submission to retry and creates duplicate customer/Set records.

**Disposition:** MUST BE IMPLEMENTED AS A HARD CONTROL. Every offline write has stable client-generated idempotency identity; server enforces uniqueness/deduplication.

### K. App crash / phone restart loses a shift

**Risk:** employee must reconstruct hours/counters/Sets.

**Disposition:** MUST BE IMPLEMENTED AS A HARD CONTROL. Active shift/events persist locally and centrally; startup reconciles/resumes rather than creating a second shift.

### L. GPS point implies exact customer address

**Risk:** GPS location is displayed/stored as though it were the customer's official address.

**Disposition:** CLOSED BY SEMANTICS. GPS Set Location and confirmed Customer Address are distinct fields. Accuracy is retained/displayed.

### M. Fake continuous route through GPS outage

**Risk:** map connects two distant points across a long outage and visually claims a route that was never observed.

**Disposition:** CLOSED BY DISPLAY CONTRACT. Honest gaps/uncertainty treatment required. Raw points are retained.

### N. Stationary GPS jitter produces fake walking

**Risk:** a stationary employee appears to wander around houses.

**Disposition:** CLOSED BY ROUTE-QUALITY LAYER. Display route filters duplicate/jitter/impossible jumps without altering raw source evidence.

### O. GPS used as proof of knocking

**Risk:** location traces/coverage are treated as proof that a specific home was knocked or a conversation occurred.

**Disposition:** CLOSED BY HARD PRODUCT PRINCIPLE. Coverage is explicitly estimated/traveled/likely worked. Door/conversation counts remain employee/system evidence from their own sources.

### P. GPS overrides municipality compliance

**Risk:** inferred city/boundary automatically authorizes canvassing.

**Disposition:** CLOSED BY HARD ISOLATION RULE. GPS may suggest Lookup input; controlled live Lookup remains authoritative.

### Q. Performance outage blocks field Lookup

**Risk:** new backend dependency makes the legally controlled field tool less reliable.

**Disposition:** MUST BE RELEASE-GATED. Performance services must fail independently. Lookup/offline core remains available when Performance is down.

### R. Background GPS is implemented as browser-only PWA

**Risk:** iPhone/Android locked/background behavior is unreliable and route freshness degrades.

**Disposition:** CLOSED BY ARCHITECTURE. Use thin native shell. iOS native background Core Location; Android location foreground service during active shift.

### S. Android permission/service complexity leaks into daily UX

**Risk:** employee must repeatedly manage Android background settings.

**Disposition:** CONTROLLED. Start the location foreground service from the visible Start My Day action; make the active tracking notification expected and explicit. Request only permissions required by the chosen implementation.

### T. iOS background tracking continues after shift

**Risk:** accidental off-shift location collection.

**Disposition:** MUST BE HARD-TESTED. Finish Day must stop native location updates/background session. App launch with no active server/local shift must not restart live Performance tracking.

### U. Pay plan changes rewrite historical commission

**Risk:** changing the current plan retroactively changes old employee pay displays.

**Disposition:** CLOSED BY EFFECTIVE-DATED VERSIONING. Every calculation records applied plan version and inputs.

### V. KPI target change rewrites history

**Risk:** September threshold makes August appear retroactively below/above standard.

**Disposition:** CLOSED BY EFFECTIVE-DATED VERSIONING.

### W. Manager correction silently changes pay/rank

**Risk:** employee disputes unexplained historical changes.

**Disposition:** CLOSED BY AUDIT CONTRACT. Original/new value, reason, actor, time, affected calculations are retained and employee-visible.

### X. Client computes privileged pay logic

**Risk:** tampering or divergent device calculations.

**Disposition:** CLOSED BY ARCHITECTURE. Compensation calculation is server-side; client displays returned calculation/provenance.

### Y. Secret backend key in mobile bundle

**Risk:** catastrophic central-data bypass.

**Disposition:** HARD RELEASE GATE. No Supabase service/secret/admin key in any browser/native client artifact. User session + RLS for normal access; privileged server-side functions for privileged operations.

### Z. Different screens calculate KPIs differently

**Risk:** My Performance says .61 while Leaderboard says .64.

**Disposition:** CLOSED BY ARCHITECTURE. One authoritative calculation service/view feeds My Performance, Team, Leaderboard, map cards, pay/coaching consumers.

## 2. UX deep audit

### Normal employee burden

Target routine work remains:

1. `START MY DAY` — one tap.
2. Add Set when needed — normal customer-name fast path or one-tap Quick Set placeholder.
3. Door/conversation counts — live counters if desired or totals only at Finish Day.
4. `FINISH DAY` — only missing inputs.

This is materially simpler than the original requested manual daily log while preserving all requested outputs.

### Screens that should not exist as standalone required workflows

Do not require separate employee forms for:

- total Sets;
- total Demos;
- total Sales;
- conversion rates;
- revenue total;
- commission total;
- weekly/monthly/60D/90D/YTD reporting;
- team reporting;
- GPS check-ins.

All are derived/synchronized.

### Cognitive-load rule

During an active shift, analytics remain secondary. The default field screen is operational. Rich historical analytics are outside Field Mode.

**Disposition: PASS AT DESIGN LEVEL.**

## 3. KPI/data-model deep audit

### Denominator rules

- `Doors = 0` → Conversation Rate N/A.
- `Conversations = 0` → Set Rate N/A unless Paradise explicitly defines another denominator policy.
- `Mature Sets = 0` → Demo Rate N/A.
- `Eligible Demos = 0` → Sale Rate N/A.
- `Hours <= 0` → all per-hour metrics N/A / data issue, never infinity.

### Time period boundaries

Must test DST/timezone boundaries even though Florida operations are currently Eastern Time. Store UTC timestamps and derive controlled local reporting windows.

### 60/90-day definition

Rolling calendar-day windows, not “two months” / “three months.” This avoids inconsistent month lengths.

### YTD definition

January 1 local time through selected/current local day.

### Outcome maturity

The system must not use one global maturity assumption if appointment date is known. Eligibility should be based on actual scheduled/outcome state where possible.

**Disposition: PASS WITH IMPLEMENTATION TESTS REQUIRED.**

## 4. Live GPS deep audit

### Precision

Every user-visible point must show age/freshness and accuracy when selected. U.S. presentation converts location accuracy to feet/miles.

### Cadence

Do not hardcode extremely frequent updates before battery testing. Location cadence should be a versioned configuration and event-aware.

### Location buffering

GPS events generated offline need stable IDs and captured timestamps so later sync does not reorder the actual route by receive time.

### Duplicate/reordered points

Server and client rendering must order by captured timestamp while retaining receive timestamp. Do not assume arrival order equals route order.

### Cross-platform behavior

The interface and route semantics are common; native lifecycle implementation differs by platform. Cross-platform tests must assert equivalent Start/Stop/Freshness semantics rather than identical OS internals.

**Disposition: PASS WITH NATIVE IMPLEMENTATION REQUIRED.**

## 5. Visibility / privacy / control audit

User direction is full Performance visibility parity between canvassers and managers. The spec therefore intentionally does not hide customer, sales, pay, GPS, route, or team Performance information from canvassers when managers can see it.

The security boundary is **mutation**, not basic Performance visibility.

Required controls:

- employee cannot edit another employee's shift/Set/outcome/pay source record;
- manager corrections are role-authorized and audited;
- admin configuration is separately authorized;
- device/session revocation is supported;
- off-shift live location is not collected by the Performance service.

**Disposition: DESIGN LOCKED; ORGANIZATIONAL POLICY/RETENTION APPROVAL REMAINS A RELEASE INPUT.**

## 6. Backend/vendor audit

### Capacitor

A thin Capacitor native shell is a strong fit because the current Paradise app is web-first and the needed native capability is concentrated in background location/device integration. A rewrite into separate native applications would increase maintenance surface without adding user value.

### Supabase/Postgres

Supabase/Postgres is a strong preferred v1 backend because SQL fits time-window KPI calculations, effective-dated business rules, audit records, geospatial/event data, realtime subscriptions, and row-level authorization. Use server-side functions for privileged changes/calculations.

### Map provider

Do not bind the data model to a map vendor. Store standard geographic points/polygons/route geometry; choose the simplest acceptable map renderer/provider during implementation. Route polylines, markers, clustering, territory polygons, and gaps are requirements independent of provider.

**Disposition: ARCHITECTURE PASS; MAP VENDOR MAY REMAIN AN IMPLEMENTATION DECISION.**

## 7. Open inputs that must not be fabricated

The specification deliberately leaves these configurable/open:

- minimum Knocks/Hr;
- minimum Sets/Hr;
- minimum Demos/Hr;
- minimum Sales/Hr;
- distinct Above Standard threshold(s), if desired;
- leaderboard minimum eligible hours/opportunities;
- Overall Score weights/guardrails, if used;
- approved pay-plan rules;
- employee roster/IDs;
- CRM/LeadPerfection current integration mapping;
- territory geometry source;
- GPS-detail retention duration;
- completed-period reconciliation/finalization window.

Implementation may build the engine/configuration surfaces without inserting invented business values.

## 9. Final audit conclusion

The proposed v1 is internally coherent if implemented as specified. The design successfully separates:

- simple canvasser actions from complex backend calculations;
- visibility from mutation authority;
- GPS operational evidence from legal/field authority;
- live period estimates from mature/final outcomes;
- current rules from historical rules;
- local offline resilience from central source-of-truth status.

No additional employee-facing feature is required before implementation foundation work begins.
